# 错了个字 · AI 手写识别接入计划(v1.0.10 起草, 替代自训 ML 路线)

> 起草日期:2026-09-18;状态:**待用户审核**(本文档为更新计划, 未动代码)
> 背景:现行识别(`src/game3/handwriting.ts` 像素重合度比对)是几何规则, 准确度差——v1.0.4 收紧误伤认真书写、v1.0.5 放松, 反复调参已近天花板, 游戏因此自 v2.5.6 维护至今。
> 新思路(用户提出):像英了个语那样**接入 AI 模型辅助识别**, 放弃自训数据集与识别模型——不再有训练数据采集、标注、训练算力与端侧内存负担(`docs/clgz_ml_plan.md` 自训路线相应搁置)。
> 已确认的技术前提:手写板为 canvas(可直接导出 PNG 图);AI 平台件(管理端配置页/限频/降级框架)在英了个语 v1.6.0 已建好, 可复用与扩展。

---

## 一、关键技术前提(与英了个语的核心差异)

1. **模态不同**:英了个语判的是**文本**, DeepSeek 文本模型即可; 错了个字判的是**手写图像**, 需要接入**视觉(Vision)模型**。
2. **DeepSeek 官方 API 目前不提供视觉模型**(deepseek-chat/reasoner 均为纯文本)——即**现有 DeepSeek Key 无法直接用于本题**, 需新增一个支持视觉的服务。候选(均为 OpenAI 兼容协议, 与现有 `_lib/aicheck.js` 架构吻合):
   - 阿里 **qwen-vl-plus / qwen-vl-max**(DashScope 兼容模式, 便宜稳定, 国内直连);
   - 智谱 **GLM-4V-Flash**(有免费额度);
   - SiliconFlow 等聚合平台托管的开源视觉模型;
   - OpenAI **gpt-4o-mini**(若用户持有)。
   管理后台「AI 检测」页的 Provider 下拉即为此预留——在 `AI_PROVIDERS` 表登记 vision 能力即可选用, Key 由用户在管理端填入。
3. **输入形式**:手写板 canvas 直接 `toDataURL` 导出 PNG(手写字迹, 无隐私信息), 以 base64 随请求提交给后端转发视觉模型。小尺寸图 token 消耗可控(单次判定约数百 token)。
4. **判定语义升级**:旧版像素重合度要求笔画位置贴近标准字形(误伤认真但结构紧凑/粗笔画的书写); AI 判定升级为「**识别语义 + 可辨认度**」——写对了(即便潦草但可辨认)即得分, 写成别的字或涂鸦无法辨认才判错。这正是 ML 计划想要的效果, 由通用视觉模型直接达成。

## 二、判定流程(新)

```
玩家提交手写
  → 前端导出卡面 PNG(base64)
  → POST /clgz/api/ai {image, target(目标字), charSet?}
  → 后端转发视觉模型: 「图中手写的一个汉字是什么? 是否为『目标字』? 书写是否工整可辨认?」
  → 返回 {ok, isTarget, recognized, legible}
      ├ isTarget=true  且 legible → 得分, 提示「识别为『X』, 正确!」
      ├ isTarget=false 且 legible → 不得分, 提示「AI 识别你写的是『Y』——不是目标字『X』」
      └ 不可辨认(涂鸦/残缺)     → 不得分, 提示「书写难以辨认」
  → AI 不可用(未配置/超时/失败) → 自动回退现行像素重合度判定(旧行为, 游戏永不可用卡死)
```

- 目标字本就展示在题面(如「锥形瓶」要求写"锥"), 无泄题问题;
- 服务端只做转发与限频, 判定结果由模型给出; 每次判定计入审计日志样本量统计。

## 三、分阶段实施计划

### 阶段 1 · AI 平台件通用化(基建, 复用英了个语框架)
- `_lib/aicheck.js` → 新增视觉能力: `AI_PROVIDERS` 表扩展 vision 字段(支持视觉的提供商登记); 新增 `recognizeHandwriting(env, imageBase64, target)`(构造 OpenAI 兼容视觉请求: content 数组 text+image_url(base64), JSON 输出 `{is_word→is_target, recognized, legible}` 契约同英了个语风格);
- 配置通用化: KV 配置键按游戏隔离(`ai:config:ylgy` / `ai:config:clgz`), 管理后台「AI 检测」页支持**按游戏分别配置**(提供商/模型/Key 可不同, 也可共用同一 Key);
- 限频复用 `windowRate`(英了个语同款)。

### 阶段 2 · 错了个字判定接入
- 新增 `functions/clgz/api/ai.js`: POST {image(base64), target} → 限频(每 IP 每分钟 20) → 转发 recognizeHandwriting → 返回结果; `_routes.json` 加 `/clgz/api/*`;
- 前端 `ClgzPage/HandwritingPad`: 提交时导出卡面 PNG → 「AI 识别中…」加载态 → 结果反馈文案(正确/错字/潦草三分, 引用 AI 识别出的字——**教育反馈升级**: 玩家能知道自己实际写成了哪个字);
- AI 不可用 → 自动回退像素重合度(旧行为), 游戏不卡死;
- 提交判定核心(`handwriting.ts`)保留为降级路径与离线兜底。

### 阶段 3 · 解除维护(游戏重新开放)
- 判定链路实测稳定后: 恢复 HubPage「错了个字」卡片(维护中 → 可玩)、`App.tsx` 路由、玩法介绍文案更新(「写对且能认出即可得分,AI 智能识别」);
- 题库(165 字清单)不变; 排行榜/结算/改名等框架不动。

### 阶段 4 · 可选增强(后续)
- **混合判定省成本**: 像素重合度高的直接通过、极低的直接拒, 中间地带才调 AI(可省大部分调用);
- **识别反馈教育化**: 展示「你写的是『勇』, 目标字是『嬴』」对比(嬴政考点);
- 笔迹样本自愿贡献(仅明示同意后)可日后用于自训模型——ml_plan 路线并未废弃, 而是被 AI 判定替代为过渡方案。

## 四、成本与风险

| 项 | 评估 |
|----|------|
| 调用成本 | 视觉模型单次判定约数百 token; 以 qwen-vl-plus/GLM-4V-Flash 计, 单局 8 题 ≈ 几分钱人民币; 限频 + 结果缓存兜底 |
| 延迟 | 视觉模型 1~3s/次, 提交后「AI 识别中…」加载态(同英了个语) |
| 防滥用 | 每 IP 每分钟限频 + 结果 KV 缓存(同笔迹同判定); 游戏维护期开放后可视情况加每日上限 |
| 隐私 | 手写字迹图不含个人身份信息; 仅用于本次判定, 不做训练留存 |
| 回归风险 | AI 判定与旧像素判定可能结论不同(更宽容)——玩法介绍明示判定标准; 像素重合度保留为降级路径 |

## 五、需要用户准备/决策的事项

1. **视觉模型服务与 Key**: 从候选中选一家(建议 qwen-vl-plus 或 GLM-4V-Flash 起步), 注册获取 API Key——在管理后台「AI 检测」页即可配置, 无需改代码;
2. **判定标准确认**: 「写对且可辨认即得分」替代旧「像素重合度达标」——是否认可(这将显著提升认真书写者的通过率);
3. **维护解除时机**: 阶段 2 上线并实测稳定后即恢复开放, 还是先内测若干局;
4. 旧 `docs/clgz_ml_plan.md` 自训路线标记搁置(数据采集/训练不再执行), 文档保留备查。
